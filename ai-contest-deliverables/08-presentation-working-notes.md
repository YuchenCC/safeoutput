# Safe Output 竞赛 PPT 工作稿

## 1. 整体风格基调

### 1.1 定位

本 PPT 是 AI 编程大赛成果汇报，不做营销型产品发布，也不做纯技术培训。叙事重点是：

- 选择了一个真实老系统问题：Java 8 / Spring Boot 2.x 输出侧敏感信息治理。
- 通过 AI 主导完成一个边界清晰、可接入、可验证的 Java starter。
- 以个人前端背景挑战 Java 基础组件研发，展示 AI 时代跨技术栈交付的可能性。

### 1.2 视觉关键词

- 工程感
- 克制
- 可信
- 可追溯
- 有竞赛答辩的完成度

### 1.3 设计方向

- 主视觉采用浅色技术汇报风格，背景以白色、浅灰、淡蓝灰为主。
- 强调色使用蓝、青、绿色表达工程、治理、安全和验证，不使用大面积紫色渐变或深色驾驶舱。
- 页面结构以“一个核心观点 + 一个证据对象”为主，避免堆满卡片。
- 核心证据对象优先使用：流程图、架构图、时间线、模块地图、测试结果表、Demo 截图。
- 技术标签保持准确，例如 `ResponseBodyAdvice`、`Log4j2 %safeOutputMsg`、`MaskMetricsCollector`、`项目记忆`。

### 1.4 叙事节奏

15 分钟、约 20 页。整体节奏按四段推进：

1. 为什么选这个题：真实痛点、AI 适配度、个人挑战。
2. 做出了什么：Safe Output 的组件定位和治理闭环。
3. AI 怎么做出来：PRD、issue、实现、测试、文档、记忆交接。
4. 如何证明可信：Demo、测试、黑盒验证、安全边界、总结。

### 1.5 页面规则

- 每页只承担一个核心判断，不把多个结论挤在同一页。
- 标题尽量写成观点句，而不是名词标签。
- 每页必须能回溯到项目代码、项目记忆或 `ai-contest-deliverables/` 中的事实。
- 不写未确认能力，不承诺 Spring Boot 3、Logback、WebFlux、数据库持久化、Dashboard 内置权限等能力。
- 不展示真实敏感原文；raw 明文只允许作为 Demo mock 兼容演示，并需明确标注风险统计。

- 压缩为一行小字：

### 第 3 页：为什么选择这个课题

页面定位：

- 承接第 2 页的 AI 工程实践方法，进入官方课题背景。
- 先讲清楚为什么敏感信息脱敏需要被做成通用工具。

建议标题：

- 选题背景：被反复验证的治理痛点

内容结构：

1. 官方课题痛点。

- 各系统按要求自行实现脱敏。
- 实现方式分散，规则口径不一致。
- 需要通用工具覆盖显示与打印。

2. 个人管理现场观察。

- 在团队管理过程中，这个痛点反复出现。
- 讨论组件沉淀时，研发仍倾向改各自系统。
- 背后的顾虑主要有三类：
  - 老系统一致性不足，沉淀组件看起来更耗人力。
  - 没有全量待脱敏清单，只能靠查缺补漏推进。
  - 老系统变量命名各不相同，很难相信一个组件可以简单全覆盖。

3. 个人判断。

- 组件沉淀必要：分散治理会持续放大成本。
- 痛点可以产品化：高频问题值得收集实现。
- AI 降低试错成本：先验证组件化可行性。

建议页面结构：

- 三层递进结构：
  - 官方命题：自行脱敏、写法不一致、效率低效果差。
  - 现场阻力：老系统不一致、清单不完整、变量命名不统一。
  - 我的判断：组件必要、痛点即需求、AI 降低试错成本。

底部收束：

- “本项目希望验证：组件化工作能否借助 AI 推进到可交付状态。”

视觉建议：

- 用三段纵向递进或阶梯式结构，不使用夸张安全警报视觉。
- 第一层是“官方痛点”，第二层是“现场阻力”，第三层是“个人判断”。
- 关键词可出现：`annotation`、`yaml`、`response`、`log`、`standard`、`AI`。

### 第 8 页：快速接入

页面定位：

- 拆解第 6 页的“快速接入”。
- 解释低侵入接入为什么能降低老系统改造成本。
- 回应前文痛点：老系统不适合深入业务代码逐个修改 Controller、DTO 和日志打印点。

建议标题：

- 输出侧低侵入接入

核心观点：

- 老系统改造成本高，不适合要求每个系统深入业务代码逐个改造。
- Safe Output 将脱敏能力放到输出侧，通过 starter、注解、配置和日志 pattern 接入。

三层接入：

1. **Response 侧：自动接入**
   - `ResponseBodyAdvice` 在接口返回前处理响应对象。
   - 价值：减少 Controller 手写脱敏。

2. **字段侧：按需声明**
   - `@Desensitize` 和 `rules[]` 兼容新老代码。
   - 价值：新代码用注解，老系统用配置。

3. **日志侧：替换 Pattern**
   - Log4j2 `%safeOutputMsg` 处理日志 message。
   - 价值：减少日志打印点改造。

底部收束：

- “快速接入的关键，是把改造点收敛到输出链路和规则配置上。”

视觉建议：

- 左侧放“老系统业务代码”，右侧放“输出侧接入层”。
- 三条接入路径分别标记：`ResponseBodyAdvice`、`@Desensitize / rules[]`、`%safeOutputMsg`。
- 每条路径旁都保留一句业务价值，避免变成技术名词堆叠。

### 第 11 页：统一规则链路

页面定位：

建议标题：

核心观点：

- 过去接口、日志、手动处理可能各写各的脱敏逻辑。
- Safe Output 将三类输出入口收敛到同一套字段识别、类型标签和脱敏策略。

三路归一结构：

1. **过去的分散写法**
   - Controller 处理 Response。
   - 日志打印前手动替换。

   - 报告统计口径一致。

底部收束：

### 第 14 页：SDD + TDD 约束 AI 产出

页面定位：

- 专门解释如何约束 AI，避免只生成“看起来像对的代码”。
- 承接第 13 页流程：流程对照说明 AI 参与研发，SDD/TDD 说明如何提升结果可信度。

建议标题：

- 规格、任务与测试约束

核心观点：

- AI 执行效率越高，越需要明确边界和验收。
- Safe Output 用 issue 连接规格与测试，让实现始终对应可验收任务。

三段链路：

- `SDD 规格先行` -> `Issue 可执行工作单` -> `TDD 测试兜底`

左侧：SDD 规格先行

- **Specification Driven Development**
- 明确需求、边界、非目标和验收口径。
- PRD 和项目记忆是 AI 的工作说明书。
- 作用：控制范围、保留决策、守住边界。

中间：Issue 可执行工作单

- 把规格拆成可执行工作单元。
- 每个 issue 包含 `Build`、`AC`、`TR`、`blocked_by`。
- 作用：连接规格约束与测试验证。

Issue 示例：

- 右下角小示例即可，不铺满页面。
- 示例：`.scratch/safe-output-mvp/0003-built-in-mask-strategies-and-id-card-validation.md`
  - `Build`：实现手机号、身份证、银行卡、邮箱等内置策略。
  - `AC`：异常格式不抛错，身份证校验覆盖日期和校验位。
  - `TR`：每种策略覆盖正常、空值、短值、非法格式测试。
  - `blocked_by`：依赖核心模型和策略接口。

右侧：TDD 测试兜底

- **Test Driven Development**
- 用测试验证行为是否正确。
- 单元测试、集成测试、黑盒测试逐层验证。
- 作用：用可复查结果确认行为正确。

底部收束：

- “SDD 解决做什么、不能做什么；Issue 拆成可执行任务；TDD 验证做得对不对。”

视觉建议：

- 三段结构：左边 SDD，中间 Issue，右边 TDD。
- Issue 作为桥梁节点，连接“规格约束”和“测试验证”。
- 右下角放 `0003 内置脱敏策略` 小示例。
- 只放关键证据标签：`PRD`、`Issue`、`项目记忆`、`Unit Test`、`Integration Test`、`Black-box Test`。
