## What to build

整理一份面向评委和初次接触项目读者的参赛项目总述，作为参赛初评看到的第一份材料。文档应在短时间内说明 Safe Output 的真实问题背景、目标用户、核心能力、赛道匹配点和最终可演示成果，并突出“面向 Java 8 / Spring Boot 2.x 老系统的低侵入输出侧脱敏 starter”。

本材料不应只写成普通项目简介，还需要额外补充“组件痛点调研”“组件实现难点”“AI 原生研发难点”，用于提高初评分辨度。整体叙事应把 Response、Log4j2、主动脱敏、聚合报告和可选 Dashboard 串成一个完整治理闭环：业务接口产生敏感输出 -> Response 自动脱敏 -> Log4j2 日志同步治理 -> 主动脱敏复用统一策略 -> 聚合统计形成风险画像 -> 报告/Dashboard 输出治理建议。

痛点调研应覆盖：Java 8 / Spring Boot 2.x / 内部 JUP 统一 Java 8 平台等存量系统多，且存在大量敏感数据输出治理需求；当前治理主要依赖人工收集接口、日志和字段清单，再在业务代码中植入转换方法；各系统缺少统一写法和统一治理清单，字段变化、接口新增、团队交接后难维护；大量系统间上下游日志未脱敏，缺乏全局日志脱敏方法；日志、报告、规则建议如果保存原始 response、完整日志或敏感样本，组件本身会变成新的泄露源；安全组件不能为了脱敏影响业务可用性，需要 fail-open、低侵入接入和可控性能边界。

实现难点应覆盖：Response 对象递归脱敏要处理 Bean、Map、集合、数组、嵌套对象、循环引用、最大深度和配置路径；规则命中要统一注解、配置、默认规则、ignore 和 fallback，并保留明确优先级；Log4j2 日志只做轻量 JSON-like/key-value 识别和有限 fallback，不能粗暴全局正则，也不引入重 JSON Parser；报告只能保存聚合指标、类型、计数、接口标识、脱敏 evidence 和治理建议，不能保存敏感原文；Dashboard 要体现治理闭环，但保持可选附加包定位，不膨胀为权限系统、数据库或完整治理平台；组件要兼容 Java 8 / Spring Boot 2.x，避免 Boot 3 API 和不必要依赖。

AI 原生研发难点应覆盖：AI 不只是生成代码，还参与 PRD 拆解、issue 化、实现、测试、文档同步和交接记忆维护；安全类项目必须约束 AI 不编造指标、不保存敏感样本、不为了演示效果放宽安全边界；通过 `CONTEXT.md`、`.codex-memory/`、PRD、issue、测试和文档约束 AI 的连续产出，避免多轮迭代中遗忘历史决策；AI 生成实现必须被测试和边界文档反向校验，尤其是 fail-open、不保存原文、未知 type、ignore 风险统计等规则。
